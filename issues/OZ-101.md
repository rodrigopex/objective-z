## Context

Split out of the oz_static parity work (`tools/oz_static/PARITY.md`), where
it was deliberately scoped out: closing it needs a design pass of its own,
not another gap fix. Everything else in that plan has landed.

`tools/oz_static/src/staticbar.rs` hard-rejects the reflection selectors and
`@selector(...)`:

```rust
"respondsToSelector:",
"performSelector:",
"performSelector:withObject:",
"performSelector:withObject:withObject:",
"isKindOfClass:",
```

plus `selector_expression` (`@selector(...)`), which the grammar does give
its own node kind.

The rejection is a located, named error, not a silent degradation, so
nothing miscompiles today — a program using these simply does not build
under the static backend.

## Input

```objc
if ([obj respondsToSelector:@selector(poke)]) {
        [obj performSelector:@selector(poke)];
}
if ([obj isKindOfClass:[Widget class]]) {
        ...
}
```

## Observed

`oz2c` exits non-zero with a located diagnostic naming the unsupported
selector. No output is written.

## Expected

A design that answers these at compile time, with **no heap and no runtime
registry** — the constraint that makes this worth its own issue rather than
a port of what the Python pipeline does.

Sketch of the shape, not a decision:

- `@selector(name)` becomes a `const` index into a generated selector table,
  not an interned string. The whole set of selectors in a program is known
  at transpile time; oz_static already computes it for the protocol-dispatch
  tables (`companion::render_protocol_dispatch`).
- `respondsToSelector:` becomes a lookup in a `const`, `class_id`-indexed
  bitmap or sorted table — the same `class_id` the dealloc and
  protocol-dispatch switches already key on
  (`_meta.class_id`, `OZ_STATIC_CLASS_*`).
- `performSelector:` needs a uniform call shape, which is the hard part: the
  existing dispatch tables are per-selector and therefore already typed.
  A generated `switch` per (selector, class) pair keeps it typed at the cost
  of code size; anything more general reintroduces a variadic trampoline,
  which is what the retired legacy runtime did with per-architecture
  assembly (`src/runtime_legacy/`).
- `isKindOfClass:` is the easy one: the class hierarchy is fully known, so
  it is a compile-time-generated ancestry check over `class_id`, and
  `Program::is_descendant_of` already computes exactly that relation.

## Workaround

None needed for the current corpus or samples: nothing under `samples/`,
`tests/behavior/cases/` or `tests/adapted/` uses these selectors, which is
why the parity work never had to face it.

## Discussion

- **MAINTAINER (2026-08-30):** Worth stating plainly what parity means here.
  The Python pipeline's "support" for these is trivial AST passthrough --
  it emits the call and lets the C compiler fail on it -- so matching the
  oracle is not the goal and would be a regression against oz_static's
  "never silently degrade" rule. The rejection oz_static has today is
  already the better behaviour; this issue is about replacing it with real
  support, not about reaching parity.
- **MAINTAINER (2026-08-30):** `isKindOfClass:` and `respondsToSelector:`
  look separable from `performSelector:` and could land first: both are
  pure predicates over facts the program already has, needing no call
  machinery. `performSelector:` is where the design cost sits.
