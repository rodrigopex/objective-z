## Context

PR #224 makes `OBJZ_BACKEND_STATIC` the default. What justifies that is
behavioural: 73 of 73 corpus cases produce identical results under both
backends, and 13 of 13 samples build, run and match their own `sample.yaml`
on `mps2/an385` under QEMU.

Two things that would normally inform a default-backend decision were not
measured at all.

## Observed

**Code size is not compared.** Both backends emit plain C for the same
programs, so the comparison is straightforward and has never been made. The
ARM sweep recorded flash figures for the static backend alone
(`hello_world` 13928 B, `arc_demo` 17448 B, `zbus_objc` 47032 B, ...) with
no Python-backend figures beside them. This matters more than usual here
because the two make genuinely different codegen choices that show up in
size:

- oz_static devirtualizes by class-hierarchy analysis, emitting a direct
  call where no subclass overrides and a `class_id` switch where one does.
- The Python backend emits a per-class `static inline` allocator into each
  header; oz_static emits one out-of-line function per class into the
  companion.
- oz_static's `@synchronized` allocates a per-block spinlock on the stack;
  the Python backend allocates an `OZSpinLock` object.

`benchmarks/` and `just bench-mem` exist and are the obvious place to do
this rather than by hand.

**Nothing has run on real hardware.** All verification is QEMU
`mps2/an385`. `hardware-map.yaml` and `just test-bench`
(`--device-testing --hardware-map`) exist, and `nrf52833dk/nrf52833` is a
documented board. QEMU does not exercise real `k_mem_slab` contention, real
interrupt-disabled critical sections, or timing.

## Expected

- Flash and RAM per sample, both backends, same board, in a form that can be
  re-run — a table in `benchmarks/` or `tools/oz_static/PARITY.md`.
- At least one sample run on `nrf52833dk/nrf52833`, `arc_demo` being the
  most informative since it is the one whose QEMU output was checked
  byte-for-byte against the Python backend.

Neither is expected to change the default on its own. The point is that the
default was switched on behavioural grounds and the size/hardware
consequences are currently unknown rather than known-acceptable.

## Workaround

`CONFIG_OBJZ_BACKEND_PYTHON=y` in a target's `prj.conf` reverts that target,
if size or on-hardware behaviour turns out to matter for it.

## Discussion

- **MAINTAINER (2026-08-30):** Filed as one issue rather than two because
  they share an owner and a setup: whoever has a board attached is the person
  who can also produce trustworthy size numbers for it.
- **MAINTAINER (2026-08-30):** If the size comparison lands first and is
  unfavourable, that is worth knowing before anyone builds on the new
  default — the devirtualization choice in particular trades a switch for a
  direct call and could go either way per program.
