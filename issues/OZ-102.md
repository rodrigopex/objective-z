## Context

Came out of making oz_static the default backend. Every sample was swept by
transpiling it, compiling and linking the generated C on host, running the
binary, and checking its console output against the sample's own
`sample.yaml`. That sweep is the strongest cheap check available: it is what
found a use-after-free in `transpiled_led` (a chain of objects each holding
the previous in a strong ivar) and a leak of every heap-allocated object in
`heap_alloc`. Neither compiling nor linking showed either one.

Three of the twelve samples cannot take part, and the reason is worth
recording precisely, because it is narrower than "they are Zephyr samples":

| Sample | What actually blocks a host build |
| --- | --- |
| `arc_demo` | `K_THREAD_DEFINE` — kernel thread creation |
| `gpio_demo` | device tree (`DT_*`, `GPIO_DT_SPEC_GET`) + GPIO driver API |
| `zbus_objc` | zbus message bus (`ZBUS_CHAN_DEFINE`, observers) |

That is kernel and driver *infrastructure*: things with no meaning off
target, which a stub cannot honestly stand in for. Everything else needed
only `printk`, and stubbing that one symbol
(`tests/behavior/include/zephyr_stubs/zephyr/sys/printk.h` plus
`tests/behavior/zephyr_stubs.c`) moved four samples straight from
"Zephyr-blocked" to running: `pool_demo`, `transpiled_blocks`,
`transpiled_generics`, `transpiled_led`.

## Observed

The samples that exercise the *language* — classes, protocols, ARC,
categories, blocks, literals, generics, `@synchronized`, dot syntax — are
tangled together with the ones that exercise *Zephyr integration*. So a
language feature that only appears in `arc_demo` or `zbus_objc` gets no host
coverage at all, and the fastest feedback loop in the project cannot reach
it.

`arc_demo` is the clearest case: its whole subject is ARC, which is pure
language semantics, and the only thing keeping it off host is one
`K_THREAD_DEFINE` for a thread that exists to show ARC working on a second
thread.

## Expected

More samples that use no Zephyr API at all, so they can be built, run and
regression-checked on host — and in CI, with sanitizers, without a
cross-toolchain. Roughly:

- One per language area not already covered host-side, each with a
  `sample.yaml` stating its expected output so the sweep can check it.
- Where a sample's subject is a language feature and the Zephyr dependency
  is incidental (`arc_demo`'s thread), consider splitting it: a portable
  sample for the semantics, and a separate Zephyr one for the integration.
- Keep the genuinely Zephyr-bound samples as they are. `gpio_demo` and
  `zbus_objc` are *about* the integration; there is nothing to gain by
  making them portable.

Worth deciding as part of this: whether the portable samples live under
`samples/` alongside the rest, or in their own directory, given they need no
board and no `prj.conf`.

## Workaround

The behaviour corpus (`tests/behavior/cases/`, 73 cases run through both
backends by `tests/tools/cross_backend.py`) already covers the language
host-side and is the reason the gap has not hurt more. But a corpus case is
a minimal unit test, not a program: the sample sweep found bugs the corpus
did not, because whole programs allocate, chain and tear down objects in
combinations a focused case never does.

## Discussion

- **MAINTAINER (2026-08-30):** The `printk` result is the useful precedent.
  Four samples looked Zephyr-bound and were not; they needed one symbol.
  Worth checking whether anything else that looks Zephyr-bound is really
  just one or two symbols away from portable, before writing new samples.
