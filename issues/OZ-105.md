## Context

PR #224 makes `OBJZ_BACKEND_STATIC` the default and verifies it on
`mps2/an385` (ARM): all 13 samples build, all 13 pass twister. RISC-V was
not tried, and it is a documented target — `justfile` defines
`riscv_board := "qemu_riscv32"` and `CLAUDE.md` documents
`just board=qemu_riscv32 rebuild`.

This is worth doing precisely because ARM already passes. A second
toolchain is the cheapest way to find anything ARM-specific that slipped
into the generated C, and the ARM run of this same work showed how much a
new toolchain surfaces: it found five defects in twenty minutes after a full
day of green host checks (see `tools/oz_static/PARITY.md`, "On target").

## Input

```sh
west build -p -b qemu_riscv32 samples/<name>
```

Twister cannot drive this as it stands: every `sample.yaml` pins
`platform_allow: mps2/an385`, so `west twister -p qemu_riscv32` filters all
13 out. Builds were therefore driven directly, one per sample.

## Observed

**Builds: 12 of 13.**

| Sample | RAM |
| --- | --- |
| hello_world | 28856 B |
| pool_demo | 28860 B |
| transpiled_led | 29020 B |
| mem_demo | 33572 B |
| transpiled_blocks | 33896 B |
| transpiled_generics | 33980 B |
| arc_demo | 34820 B |
| transpiled_literals | 38156 B |
| heap_alloc | 41928 B |
| hello_category | 46020 B |
| zbus_service | 82652 B |
| zbus_objc | 85256 B |
| **gpio_demo** | **does not build — see below** |

`qemu_riscv32` reports no FLASH region at all; it is RAM-only. So these
figures are not comparable with the ARM sweep's flash numbers, and a
cross-architecture size comparison is not meaningful. Same-architecture
comparison against the Python backend is OZ-106.

**`gpio_demo` does not build, and it is the board, not the transpiler:**

```
zephyr/include/zephyr/device.h:96:41: error:
  '__device_dts_ord_DT_N_ALIAS_led0_P_gpios_IDX_0_PH_ORD' undeclared
zephyr/include/zephyr/devicetree.h:237:32: error:
  'DT_N_ALIAS_led0_P_gpios_IDX_0_VAL_pin' undeclared
```

`qemu_riscv32` has no `led0`/`sw0` device-tree aliases, which
`GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios)` requires. That sample's own
`sample.yaml` already restricts it to `mps2/an385`. Nothing to fix.

**The generated C is byte-identical between ARM and RISC-V.** This is the
useful result. Diffing the whole generated tree between the `mps2/an385` and
`qemu_riscv32` builds of the same sample gives zero differences, once the
manifest is excluded (it lists absolute output paths):

| Sample | Differing lines |
| --- | --- |
| hello_world | 0 |
| arc_demo | 0 |
| hello_category | 0 |
| heap_alloc (`--heap-support` path) | 0 |
| zbus_objc | 0 |

That is the design intent holding up: the PAL absorbs the target, and
nothing architecture-specific reaches the transpiler's output. It also means
a RISC-V *build* failure would have to come from the PAL, the SDK headers or
the board — not from codegen.

**Two of the three watch items in the original filing are resolved:**

- *Clang selection.* The AST dump used
  `~/.local/zephyr-sdk-1.0.1/llvm/bin/clang` — the SDK's LLVM, as intended.
  `objz_find_clang()` picks it without `OZ_CLANG`, which only the test
  harnesses honour. Dumps were real (256 KB for `main.m`, 832 KB for
  `OZString.m`), and no "no usable Clang AST dump" warning fired, so the
  ownership facts were present rather than silently missing.
- *Slab alignment.* `pools::SLAB_ALIGNMENT` is 4 and is not derived from the
  target; RV32 agrees, and nothing failed.

**The third is still untested**, and this is worth keeping in mind:
`struct k_spinlock` is empty on `qemu_riscv32` too, because `CONFIG_SMP` and
`CONFIG_SPIN_VALIDATE` are both off there as on `mps2/an385`. So the *other*
shape of that struct — the one with `locked`/`owner`/`tail` — remains
unexercised, and with it the non-trivial path through `oz_spin_init`. An SMP
board is needed for that, not merely a second architecture.

**Also noticed, not chased:** `_objz_build_ast_flags`
(`cmake/ObjcClang.cmake`) passes no `--target=`, so AST dumps run under
Clang's host default triple rather than the Zephyr target's. Harmless for
oz_static, which reads only ivar ownership and method definedness — both
target-independent. It may matter more for the Python backend, which reads
whole method bodies out of the same dumps.

## Not verified

**No RISC-V sample was executed.** Builds only. Two mechanical obstacles,
both worth knowing before the next attempt:

- `west build -t run` blocks until the guest exits, and several samples loop
  forever. Killing the ninja wrapper leaves the `qemu-system-riscv32` child
  alive — six accumulated before this was noticed, and they then collided on
  `qemu.pid` (`cannot create PID file: Resource temporarily unavailable`),
  which made subsequent runs fail for a reason unrelated to the samples.
- Driving `qemu-system-riscv32` directly with a `timeout` avoids both, and is
  what the ARM side used. The invocation is in the build's own ninja rule
  (`-machine virt -bios none -m 256 -cpu rv32i,...`).

So this issue stays open. The remaining work is execution: run each build
and check it against its own `sample.yaml`, whose expectations are
board-independent and can be reused as-is.

## Workaround

None needed. ARM is the verified platform. RISC-V builds; whether it behaves
is unmeasured.

## Discussion

- **MAINTAINER (2026-08-30):** The byte-identical generated C is the finding
  that most reduces the risk here. Whatever is left to discover on RISC-V is
  in the PAL, the SDK headers or the board — the transpiler emits the same
  bytes either way, which is exactly what it was designed to do.
- **MAINTAINER (2026-08-30):** If twister is wanted for RISC-V, the
  `platform_allow` lists have to grow `qemu_riscv32` — except `gpio_demo`'s,
  which is correctly board-specific. Worth deciding deliberately rather than
  widening them all.
